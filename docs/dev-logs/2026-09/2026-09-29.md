## Bug 修复（详情见 `docs/KNOWN_BUGS_AND_FIXES.md` §4）
- **现象**：`/talent`「天赋来源」弹窗的 ✕ 掉在卡片外面、悬于视口右侧垂直居中处。弹窗越矮越明显。
- **根因**：`App.vue` 的 `<style>` 非 scoped，其中裸选择器 `.modal-close-x { position:absolute; right:12px; top:50%; transform:translateY(-50%) }` 本意只服务 `.import-modal-card`；
  而 8 个页面的 scoped `.modal-close-x` **只声明颜色/字号等、不声明 `position`**，scoped 规则特异性虽高却只在**它声明过的属性**上赢，
  于是绝对定位泄漏全站；页面的 `.modal-header`/`.modal-window` 均为 static，最近定位祖先成了 `position:fixed` 的 `.modal-overlay` → 按视口定位。
- **修法**：全局规则收窄为 `.import-modal-card .modal-close-x`（含 `:hover`）。页面 X 回到 `.modal-header` 的 flex 布局（各页本已写 `justify-content:space-between`）。
- **实测**（390×844）：修复后 `position=static`、X 中心 (340,382) 落在卡片头部；注入旧规则则 `position=absolute; top=422px; right=12px`、X 中心 (362.6,422) 越出卡片右缘 —— 与用户截图一致。

### 天赋品质下拉框：被裁 + 跳位（详情见 `KNOWN_BUGS_AND_FIXES.md` §5）

同处一屏的两个缺陷，一次修完：

- **① 下拉框底部被滚动容器裁掉**。绝对定位**逃不出 `overflow` 裁剪**：下拉框的包含块 `.talent-tag-dropdown-wrapper` 就在滚动容器内部，容器 `overflow-y:auto` 会裁掉溢出的后代（`z-index` 再高也没用，只有 `position:fixed` 不受影响）。
  实测（`.talent-list` 底 = 829）：卡片贴 85% 时下拉框 `[676→810]` 完整；贴 95% 时 `[744→878]` **裁掉 49px**；贴 100% 时 `[778→912]` **裁掉 83px** —— 第 3 项只剩半个字、第 4 项完全不可见，与用户截图吻合。
  → 修法：新增 `measureDropUp()`，展开前量下方剩余空间，不够就给菜单加 `.drop-up`（`top:auto; bottom:100%`）向上弹。
  **向上找最近的裁剪祖先、不写死类名** —— `/talent` 的裁剪层是 `.talent-list`，而 `/search` 的 `.talent-list` 没有 `overflow`，真正裁剪的是上层 `.app-content`。
- **② 切换品质后卡片在列表里跳位**。`switchQuality` 写 `item.step`，而 `primarySortedTalents` 正是按 `step` 权重排序 → 切到较低品质就往下沉（实测「强而有力」S→A，序号 5 → 6，与「意志强韧」互换）。
  → 修法：新增 `sortVariantOf(t) = t.qualities[0] || t`，**排序身份固定取组内默认（最高）品质**；`getCategoryOrder`、`sortRule`、`selectedCharacter` 分桶全部改走它。
- **顺带修**：`switchQuality` 原本还会写 `item.uid`，而它是 `v-for` 的 `:key` → 改 key 会让 Vue **销毁重建整张卡片**（图片重新加载、下拉框闪一下）。已不再改写 `uid`。
- **注意事项（两处易错）**：菜单高度必须在 `await nextTick()` 之后量真实值，不能硬编码项高；`event.currentTarget` **只在事件派发期间有效**，必须在 `await` 之前取出，否则是 `null`。

- **③ 下拉框被下一张卡片盖住（层叠上下文陷阱）** —— 用户二次反馈后追查出来的，**第一轮漏掉的那个**。
  现象：下拉框与下一张卡片重叠的那段被下一张卡片整体盖住，最后一项只剩上半截。
  根因：`.talent-card:hover { transform: translateY(-2px) }` 的 `transform` 让卡片成为**层叠上下文**，
  但卡片是 `position: static`，**仍按普通流绘制** → 卡内下拉框的 `z-index: 1000` 被**困在卡片内部**，
  后面 DOM 顺序的兄弟卡片在普通流里绘制得更晚，于是盖住它。
  修法：悬停规则**同时**写 `position: relative; z-index: 30`，让卡片整体进入"正 z-index 层"。
  > **为什么第一轮没查到**：探针用 `element.click()` **程序化点击**，不触发 `:hover` → 卡片没有 `transform`、
  > 没有层叠上下文 → 下拉框正常浮在上面，测出一个假的"通过"。改用 `page.mouse.move()` + `click()` 做**真实悬停**后才复现。
  > 触屏上点按后 `:hover` 会**粘住**，所以手机端一直也是坏的。

- **④ 热更包条目带 `./` 前缀 → App 全量更新失败**（`KNOWN_BUGS §6`）—— 发版后用户实机反馈。
  现象：App 弹「热更新 / 更新失败 / 热更新包缺少 index.html」，重试无效，**所有用户都中招**。
  根因：`pack-hotupdate.mjs` 用 `tar -a -c -f dist.zip -C staging .`，**bsdtar 把末尾的 `.` 展开成 `./`**，
  于是 4555 个条目全带前缀，`index.html` 实际叫 `./index.html`；而前端
  `unzipped['index.html']` 是**按精确键名**取 → 取不到 → 抛错。
  **更值得记的是校验为什么没拦住**：打包器自己那条校验 `tar -tf` 后做了 `.replace(/^\.\//,'')`，
  **恰好把前缀洗掉**，于是脚本"自认为通过"把坏包放行上线 —— **校验与被校验的消费方不同构，等于没校验**。
  修法：
  ① 打包改为**逐个列出 staging 顶层条目**（条目名即 `index.html` / `assets/…`），并把校验换成
  **用前端同一个 fflate、按精确键名验**，外加"任何条目不许带 `./` 前缀"的硬断言；
  ② `hotupdate.js` 加兜底 `unzipped['index.html'] || unzipped['./index.html']`（带前缀的包本是**合法包**，
  判它"缺 index.html"属过度严格）—— 但这条要**下次发 APK 才生效**，救不了已装机用户，故第 ① 条才是正解。
  新增常驻工具 `tools/verify-hotupdate-package.mjs`，**双向自检**：好包「通过 —— 可以上传」、
  坏包「失败 N 项，不要上传」。

- **⑤ 热更包中文文件名编码错误 → 原生解压 `MALFORMED`**（`KNOWN_BUGS §7`）—— 修完 ④ 重发后的**第二个坑**。
  现象：错误从「缺少 index.html」变成「**MALFORMED[1]**」；用 Bandizip 打开包，`备用/` 显示成 `����`。
  **用户自己用 Bandizip 压一份则完全正常** —— 这一句直接锁定了"是打包工具的问题"。
  根因：bsdtar 在 Windows 上按**本地 ANSI 码页（GBK）**写文件名，**且不置 UTF-8 标志位（bit 11 / `0x800`）**。
  实测同一中文名：bsdtar → 字节 `b1b8d3c3` flag=`0x0008`；fflate → 字节 `e5a487e794a8` flag=`0x0800`。
  失败链路：JS 侧 fflate 按 CP437 解出乱码键，但 `index.html` 是 ASCII 能过闸 → 交给原生 →
  `java.util.zip.ZipInputStream` 按 UTF-8 解 GBK 字节失败 → `ZipException: MALFORMED`。
  修法：**打包整体改用 fflate 的 `zipSync`**（与前端读包同一个库），并给逐文件**固定 `mtime`** 使输出
  **字节级可复现**；打包器新增硬断言「含非 ASCII 的条目名必须置 `0x800`」。
  验证用**独立实现**交叉确认（`.NET ZipFile` + 手写中央目录解析器，刻意不用 fflate 自证）。

- **⑥ 整页角色头像全变成占位图**（`KNOWN_BUGS §8`）—— 用户实机截图反馈。
  现象：`/talent-manage` 每一行的角色头像都是**同一张**通用占位图，连角色名都分不出来。
  根因：**页面自己给 `<img>` 挂了 `@error`，抢在全局换装之前把 src 换成兜底图**。
  WebP 化后 `Header` 只剩 24 个 `.png`（214 个是 `.webp`），模板拼的 `/Header/{id}.png` 大量 404，
  本来全靠全局 `handleImageError` 换装救回 —— 被页面 `@error` 抢先就全退成同一张图。
  影响 6 个页面：`TalentManageView`（5 处）、`SubSkillView`、`UniqueView`、`RelicsView`、`RoleView`、
  `PrefixView`（`failedIcons` 记失败后 `getPrefixIcon` 返回 null，重渲染即丢图）、
  `GambleShopView`（`iconPath=''` 退文字占位，丢掉本可显示的图标）。
  修法：① `App.vue` 新增按目录兜底表 `DIR_FALLBACK`，第 3 层不再一律退通用头像；
  ② 删掉 5 个页面所有"覆盖 src"的 `@error`；③ `PrefixView` 删掉 `failedIcons` 那层状态；
  ④ `GambleShopView` 保留文字占位语义，但自己做一次换装（页面私有标记，不依赖监听器顺序）。
  实测：`/subskill` 退兜底 **10 → 0**、`/unique` **6 → 0**、`/prefix` 图标 **48 → 53 个**。
  新增巡检 `tools/verify-avatar-health.mjs`，判据是"**最终有没有退成兜底图**"——
  原 `verify-image-health.mjs` 查的是裂图（`naturalWidth===0`），而这里图片是"加载成功"的，**抓不到**。
  > 探针教训：静态服务**缺文件必须真返回 404**。第一版为了 SPA 回退把 404 伪装成 `200 + index.html`，
  > 导致"404 监听"永远抓不到，测出来的结论是假的。

### 附：为什么包体从「14 MB」掉到 8.53 MB（体积口径订正）

发版后被问"包怎么突然变小了"，逐提交量了 `public/` 才定位清楚 —— **不是本次改动，是 2026-09-28 的图片 WebP 化**（`a854a3b`）：

| 提交点 | `public/` 参与打包 | `.png` | `.webp` |
| --- | --- | --- | --- |
| `07e6c80` 2026-09-26 | **12.03 MB** | **8.15 MB** | 0.86 MB |
| `a854a3b` 2026-09-28（WebP 化） | **7.78 MB** | 1.03 MB | **3.88 MB** |
| 当前 | 7.43 MB | 1.03 MB | 3.53 MB |

**同时查实文档里的一个口径错误**：`HANDOFF §7.7` 与 `SPEC §6.1` 把
「热更包 **13.70 → 11.78 MB**」当成包体记录 —— 但验算 `7.78（public 参与打包）+ 4.00（dist/assets）= 11.78`，
**那两个数是未压缩合计，从来不是 zip 包体**。真正的包体：WebP 化前约 13~14 MB，**现在 8.53 MB**。
这个混淆正是"8.53 MB 看起来像异常缩水"的根源，已在两份文档里写清口径。

> 另记一条机制：PNG 在 zip 里还能被 deflate 压掉约一成，而 **WebP 本身已压缩、zip 几乎压不动**，
> 所以 raw 上少掉的体积会接近 **1:1** 传到最终包体上 —— 这是"转 WebP 让热更包显著变小"的真实原因。
>
> 排查中还撞到一个真实的打包陷阱：有人把整个 `dist/` 压成 zip 放回 `dist/` 根层，
> 若**不加 `--build`** 直接打包，这坨 8.5 MB 会原样进热更包（包体几乎翻倍）。
> 已给 `tools/pack-hotupdate.mjs` 加防线：**dist 根层的 `.zip` 一律排除并告警**（子目录里的不误伤）。
