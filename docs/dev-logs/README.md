# 开发日志规范

开发记录统一按日汇总。同一天无论涉及多少模块、多少次修改，都只维护一份日报；废弃按单次修改、独立主题或时分秒新建日志的规则。

> 注意：所有文档均统一使用 UTF-8 编码保存。

## 1. 目录与命名

```text
docs/dev-logs/
  README.md
  YYYY-MM/
    YYYY-MM-DD.md
```

日期按项目时区 `Asia/Shanghai`。当天首次产生需要记录的改动时创建日报，后续直接合并到对应模块，不追加流水账式时间小节。跨日继续开发只记录当天新增结果，引用上一天的日报，不复制前文。

## 2. 日报模板

```markdown
# YYYY-MM-DD 开发汇总

## 核心进展 / 概述
- 当日整体工作主线与核心目标概览。

## UI 与交互
- 用户可感知的变化、受影响页面和关键实现文件。

## 数据与解析
- 原表/配置来源、字段规则、派生产物和数据更新注意事项。

## Bug 修复
- 问题现象、已确认根因、修复结果及必要回归场景。

## 重构与维护
- 公共能力调整、维护脚本、依赖、清理冗余或工程规范治理。

## 验证
- 实际执行的命令与验证结果；未执行项及原因必须明确。

## 发布与回退
- 是否需要完整构建、热更包、CDN 素材同步或 APK 重新打包。
- 涉及删除/覆盖时记录备份位置及恢复方式。

## 未完成事项
- 明确尚未解决的问题；没有则写“无”。

## 文档同步
- 已更新的权威文档；未同步项及原因。
```

无改动的模块可省略。记录最终有效实现与重要取舍，不保留反复尝试、逐条聊天回应或重复构建输出。不要把“准备执行”写成“验证通过”。

## 3. 记录与收口

- 需要记录：页面业务逻辑、数据规则、组件行为、路由架构、构建发布链、Capacitor 原生桥接或维护脚本的实质变化。
- 可不记录：只读分析、答疑、没有文件变化，或纯错别字微调。
- 阶段完成、提交或发布前集中整理日报；无需每次保存文件后写日志。
- 对照当前 `git status`（含未跟踪文件）和 `git diff` 核对实际范围，保留用户已有改动，不把别人的历史改动算成本次完成。
- 所有 Markdown 文档一律使用 UTF-8 编码保存。
